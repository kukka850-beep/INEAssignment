# Design Note — INE Price Tracker

## How I made the scraping reliable

### 1. HTTP Probe with Playwright for the Store's Required Interaction
The scraper first makes a lightweight HTTP request to validate reachability. The provided INE mock store is a client-rendered React SPA and gates the quote behind a user interaction, so static HTML parsing cannot retrieve a current price or stock value. In `auto` mode, the scraper switches to Playwright after the HTTP probe and uses Chromium to perform the interaction.

The `/quote` response contains an obfuscated payload. The scraper checks the response status and returned option ID, then reads the visible selling-price element and stock badge rendered by the store. It does not use hidden price nodes: the page includes decoy values there.

### 2. Structured Retries and Exponential Backoff
Scrapes are subject to network fluctuations, transient store timeouts, and occasional 502/504 gateway delays.
- Scraper attempts are capped at **3 attempts per run**.
- Retries use **exponential backoff with jitter** (`delay = baseDelay * 2^(attempt - 1) + randomJitter`).
- **Honest Attempt Logging:** Intermediate attempts are logged to the database as `outcome: 'retried'`; the final attempt is logged as `success`, `retried` (success after a retry), or `failed`. If a history write fails, the scraper does not silently continue as though the attempt had been recorded.

### 3. Asynchronous Content Synchronization (No Fragile `sleep()`)
Fixed sleeps are not used to decide that a price has loaded. Playwright waits for the page, consent dialog, option selection, quote response, and visible offer/stock elements. The short timed mouse movements are only to reproduce the store's hover interaction that enables its quote button.

### 4. Zero False Data ("Never Store Wrong or Empty Data")
If an attempt encounters an error, timeout, or unexpected DOM structure:
- The outcome is logged as `'failed'`.
- The `price` and `stock` fields are explicitly recorded as `NULL` in the database and empty strings in the CSV export for failed attempts.
- Stale prices are never carried over into a failed run's price column, and a price is never recorded as `0` or guessed.
- Price drop and back-in-stock alerts are only calculated when a valid, successful reading is achieved.

### 5. Multi-Option Product Variant Selection
Every product on the mock store comes with variant choices (such as storage capacity, finish, or pack sizes).
- Before extracting the price, the scraper dismisses consent, selects the option matching the user's tracked `optionLabel`, and verifies that the store marked it selected.
- When an option ID is available, the quote response's option ID must match it. A missing or mismatched option is treated as a failure, never as a successful scrape of the default option.
- The current price comes from the visible selling-price node, not the hidden decoy price nodes.

## Trade-offs I Made

1. **Per-Attempt Timeout vs. Scheduling Budget:**
   Set a timeout cap of 20 seconds per attempt (up to ~60s total across 3 attempts, plus backoff). This gives slow responses time to recover without allowing an unbounded wait.

2. **Dual-Mode Data Layer (Supabase + Local Persistent Fallback):**
   The application natively targets Supabase PostgreSQL as required. For local evaluation when remote credentials are not configured, it provides a persistent JSON adapter with the same query interface. Any local sample history is development/demo data; it is not evidence of unattended production scrapes.

3. **External Cron Triggering vs. In-Process Timers:**
   Render's free tier spins down after periods of inactivity. An in-process `setInterval` would freeze when the container sleeps. Using an external cron trigger (`POST /api/cron/run-scrapes` via cron-job.org) wakes the service up on schedule and executes pending scrapes.

## What My AI Tool Got Wrong on the First Attempt, and How I Corrected It

1. **Assumed Server-Side Rendered HTML:**
   - *What went wrong:* The initial scraper code generated by the AI attempted to parse product prices using static Cheerio CSS selectors directly from the raw HTML response.
   - *Why it failed:* The INE mock store is a client-side React SPA; the initial HTML document contains no price or stock text—only root mounting tags and JS bundles.
   - *How I corrected it:* I inspected the actual network traffic and DOM behavior in DevTools, identified the client-side quote API and Playwright requirement, and re-architected the scraper to use Playwright with verified option selection and the visible offer price.

2. **Generic Default UI with Blue Color Scheme:**
   - *What went wrong:* The initial interface generated by the AI used standard blue primary buttons (`#2563eb`), blue hyperlinked text, and generic alert cards.
   - *Why it failed:* The blue palette looked generic and did not fit the product's intended visual identity.
   - *How I corrected it:* I chose a dark slate, warm amber, and emerald palette in `theme.css` and applied it consistently to the home page, navigation, charts, and badges. This was a design choice, not a color constraint in the assignment.

3. **Silent Failures on Missing Elements:**
   - *What went wrong:* When selectors didn't match (for example, if a variant was sold out or the page showed an error banner), the initial code returned empty strings or undefined without marking the scrape as failed.
   - *How I corrected it:* Added strict schema and content validation: if expected selectors or price values are absent or non-numeric, the scraper throws a typed error, triggers the retry backoff sequence, and logs the attempt honestly as `retried` or `failed`.
